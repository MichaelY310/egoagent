# Contributing to EgoAgent

EgoAgent is split into a small runtime core, declarative assets, a local API,
and the Workbench UI. Keep changes inside the owning layer and avoid copying an
implementation into several Identities.

## Development setup

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests
cd harness_editor
npm install
npm run build
```

Run the integrated product from the repository root:

```bash
python start-all.py
```

The user-facing URL is `http://127.0.0.1:8880`. The backend API on port 8765
and the Void server on port 8869 are implementation details.

## Where changes belong

- Runtime and orchestration: root Python modules such as `agent.py`,
  `pipeline_engine.py`, `harness.py`, and `run_coordinator.py`.
- Reusable behavior: `capability_packs/`; inherit a pack instead of copying its
  Skills into multiple Identities.
- Persona and policy: `identity/<name>/id.json` and its `ego/` or `superego/`.
- DAG templates: `harness/<name>/config.json`. Internal workers should be
  clearly marked and hidden from the default catalog.
- Workspace capabilities: `<workspace>/.environment/`, `.agents/skills/`, or
  `.codex/skills/`. These receive search priority only in that workspace.
- Workbench UI: `harness_editor/src/`. Do not edit generated `dist/` files.
- Product integration bundle: generated by `npm run package:extension`.
- Experiments: `experiments/`, with durable summaries in
  `experiments/results/`. Do not put experiment snapshots in runtime modules.

`meilisearch/` is a vendored upstream source tree. It is not EgoAgent runtime
code and must not be edited as part of product changes.

## Quality gates

Before opening a change:

1. Run the focused tests for the changed component.
2. Run `python -m unittest discover -s tests` for runtime changes.
3. Run `npm run build` for Workbench changes.
4. For UI work, exercise the feature through port 8880, including empty,
   loading, error, and recovery states.
5. Keep provider keys in environment variables. Never commit `.env.local`,
   session data, SQLite runtime databases, or screenshots containing secrets.

## Capability metadata

Descriptions are retrieval input, not decoration. A Skill or Tool description
should state what it does, when to use it, its important constraints, and its
expected output. Use stable names and narrow tags. The catalog records real
activation outcomes automatically; do not seed fake usage metrics.

When no existing capability fits, create the smallest reusable capability,
test it, then reindex the catalog. Do not create aliases whose only difference
is wording.

## Context safety

Context curation must be reversible. The working prompt may contain summaries
or elisions, while `full_messages.json` remains the audit source. Preserve the
latest request, system constraints, errors needed for recovery, file paths, and
unresolved decisions. A parsing or model failure must default to keeping data.
