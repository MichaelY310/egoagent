# 真实 Harness 修改：小规模诊断

日期：2026-10-12。结论：**目前不支持把“学习组件组织方式”作为主论文方向。真实的跨组件依赖存在，但本轮自适应分组没有胜过合理固定分组。**

这是一次证据筛查与补丁拆分回放，不是已经完成的在线 RSI / solver benchmark 实验。没有调用 DeepSeek 或其他付费模型，没有修改 EgoAgent 产品代码。

## 1. 实际做了什么

两类材料严格分开：

| 材料 | 用途 | 实际执行/检查 | 不能据此声称什么 |
|---|---|---|---|
| DGM 官方公开自修改日志 | 查是否真的发生跨组件修改 | 按时间取前 40 个候选的元数据和补丁；另读最早 4 条完整 improver 对话及 initial 元数据 | 没重跑 SWE-bench 的拆分候选，不能证明跨组件提升做题分数 |
| mini-SWE-agent 真实上游提交 | 测只应用一部分真实补丁会怎样 | 时间顺序冻结 12 次提交；穷举 32 个生产代码版本；执行上游回归测试 | 不是 improver 自己生成修改，不是自动进化收益 |
| 上述样本中的 3 个接口相关提交 | 检查单元测试是否遗漏真实接线 | 复用上游错误响应/场景，连接真实适配器、loop、生产 YAML；12 个拆分版本 | 是事后补充的自写集成探针，不是新增独立样本或真实在线模型回答 |

32 个正式回放版本共记录 **1,044 个 pytest 结果项**，包括收集错误；这些结果项不是 1,044 个独立任务。正式子进程耗时合计约 **342 秒**，不含下载、审阅、环境排错与补充探针。12 个完整补丁均通过本轮适用测试。

## 2. 如何避免挑有利例子

原始协议见 `protocol.json`，选样哈希见 `results/mini_sample.json`、`results/dgm_sample_manifest.json`。

- DGM：只选 `swe_dgm` 主实验，按候选目录时间取前 40 个；不拿消融目录充独立样本。不丢弃无结果、空补丁、失败候选。
- mini：固定 HEAD `04d809ceab9df28f9adaed044884180159172930`，沿 first-parent 从新到旧，在最多 120 个提交中取前 12 个“有语义 Python 源码修改且有上游 Python 测试修改”的提交。排除记录保留；不按效果、跨组件程度或成功率挑选。
- 组件用已有目录边界：`agents/models/environments/run/config/utils/core`，不为了制造协同把一段函数切成几个组件。
- 每个提交使用完全相同的 child 版本测试，生产代码从 parent 出发，只替换对应组件的真实文件。所有组合均执行，不只测看起来有利的组合。
- 主组件 seed 在测试前固定，取语义变化 Python 文件的 diff 行数最多的组件。原协议误写成 AST 变化量；`protocol_amendment_01.json` 在测试前更正，未改变已经选好的 seed。
- 在测试前发现 Python-only 会漏掉提示词 YAML/CSS，因此在同一批提交中纳入所有 `src/minisweagent` 改动。原来的 Python-only 统计和协议仍保留。修正后 12 个提交中有 4 个跨目录组件提交。
- 没有让 LLM 提出一套专门击败固定分组的题目；没有向优化器泄露失败测试来重写分组规则。

这个取样仍有明显偏差：仅一个维护仓库、短时间窗口、必须带测试、目录级颗粒度。它适合低成本否决一个缺少证据的动机，不适合估计所有 harness 的总体规律。

## 3. 分组方法到底比较了什么

每个方法选择本次可以应用哪些组件的**现成真实补丁**。这不是让不同 improver 分别尝试写代码。

| 方法 | 测试前固定的定义 |
|---|---|
| 单组件 | 只应用 seed 对应补丁 |
| 固定分组 A | runtime=`agents,models,environments,core`；support=`run,config,utils`；选择 seed 所在组 |
| 固定分组 B（接口友好） | runtime=`agents,models,environments,core,config`；support=`run,utils`；把模型与提示词/配置放在一组 |
| 自适应依赖规则 | 在本次已知改动文件中，用 import、协议/定义引用、模板变量构图，从 seed 取依赖连通部分 |
| 完整补丁 | 应用所有真实改动，作为可达到的正确性上界 |

固定 B 在任何反事实测试前登记，见协议修订。它不是看过分数后挑出的“赢家”。自适应规则在结果出来后没有调参，基础设施测试会重新计算并核对冻结的选择。

**重要边界：自适应规则不是学出来的 organizer；它还提前知道真正修改了哪些文件。** 这是一个有 oracle 定位信息的简单代理基线。不能把它的较小名义范围直接换算为 token、搜索次数或推理效率收益。固定 B 名义选择平均 4.25 个组件、自适应 1.25 个，但两者真正应用的已修改组件都平均 1.25 个——没有测到实际搜索成本差异。

固定 B 与自适应都通过全部 **11 个非 UI 提交**，并且都漏掉同一个 UI/CSS 提交。这个非 UI 切片是为了说明差异来自哪里，不是事后把失败案例从主表删除。

结论不是“固定分组对所有未来任务已经最优”，而是：**在这次筛查中没有自适应优于合理固定分组的效果证据，更没有支持再加一层学习组织者的证据。**

## 5. 找到的真实跨组件例子

### 5.1 解析失败也扣费：适配器 + agent loop

来源：[mini-SWE-agent #915，40fa3652](https://github.com/SWE-agent/mini-swe-agent/commit/40fa36522015a6bc6cf14411382b662b42083bf1)。不是本实验制造的 bug。

问题：API 已收费，但回复解析失败；费用没有被 agent 的预算限制正确计算。

- 模型适配器必须把费用写入 `FormatError` 的元数据。
- agent loop 必须读取异常中的费用并累加。
- 只修改提供者，消费者不读；只修改消费者，提供者不给。两边都不完整。

原样上游测试：parent 56/64，只有 agents 57/64，只有 models 63/64，一起修改 64/64。注意：这些测试分别 mock 了另一侧，因此“整个测试集必须两边都修”本身只证明测试集合的合取，不是同一个行为的协同。

为检查真实接线，补充探针把上游自带坏 tool-call 响应喂给真实 OpenRouter 适配器，再连接真实 DefaultAgent。只替换网络 I/O，不改计费解析/异常传播/循环逻辑。每次成本使用原 fixture 的 0.01，预算保持上游测试的 2.5 倍单次费用比例。

| 应用的补丁 | 实际执行调用数 | loop 记录的费用 | 行为 |
|---|---:|---:|---|
| 无 / 只 agents / 只 models | 各 8 | 各 0 | 漏记费用，撞到步数上限 |
| agents + models | 3 | 0.03 | 正常因费用上限停止 |

这证明这次真实补丁确实存在**生产者—消费者依赖**。固定 A、固定 B、自适应都能覆盖，不是自适应分组的独有收益。

### 5.2 把错误工具名误报为截断：解析器 + prompt YAML

来源：[#896，147121ff](https://github.com/SWE-agent/mini-swe-agent/commit/147121ff35ba95b6e405bdc846d855dff21c00d3)。

对上游已经存在的 `shell` 错误工具调用：

| 版本 | 使用生产 YAML 后的实际反馈 |
|---|---|
| parent | 错误提示“输出被截断” |
| 只 models | 仍提示截断，旧 YAML 不用新标志 |
| 只 config | `has_tool_calls` 未定义，模板异常 |
| models + config | 正确提示 `Unknown tool 'shell'` |

上游原单元测试把新模板直接写在测试文件里，所以只改 models 就通过了 13/13；但实际产品配置仍有问题。补充探针只把这个内联模板换为生产 YAML，未另造业务题目。

固定 A 把 config 与 models 分开，因此漏掉；固定 B 与自适应均成功。**这是固定边界选择得是否合理的问题，尚不是需要从历史学出动态组织的证据。**

### 5.3 正确解释截断：响应元数据 + prompt YAML

来源：[#862，640165a5](https://github.com/SWE-agent/mini-swe-agent/commit/640165a535e6b6bcdc68f99fc447fb31154206d6)。

复用上游 `status=incomplete / reason=max_output_tokens` 的响应场景，调用各版本自己的真实 Responses 适配器 `_parse_actions`，加载生产 YAML。

- parent、只 models、只 config 都给出普通“缺少工具调用”的反馈。
- 两者一起修改才指出输出被截断。

原测试直接提供新模板，也掩盖了生产 YAML 的必要性。这里仍是显式接口/数据依赖，固定 B 已覆盖。

补充检查有三版保留：v1 有一个不必要的 fixture 导入导致旧版本 ImportError；v2 避免该导入但调用了旧版本不存在的新签名；v3 改为调用各版本自己的生产适配器。正式解释只使用 v3，不把探针自身的不兼容当作 solver 的行为失败。

### 5.4 自适应失败的反例：轨迹查看器 + CSS

来源：[#815，f874ad4e](https://github.com/SWE-agent/mini-swe-agent/commit/f874ad4e3205fe28b06be66608637f80954cd439)。

真实改动增加 reasoning 展示、切换与热重载，同时增加 CSS。

- 只 run：22/23，缺少样式断言失败。
- 只 config：18/23。
- 一起：23/23。

自适应规则没有识别出 CSS 类名依赖，只选 run。固定 A 的 support 分组反而正确覆盖。固定 B 也遗漏。

这是 UI 完整性/样式依赖，不是 solver 推理能力提高。保留这个反例，未为了改进自适应分数补一个 CSS 特判。原上游单个测试中，也没有观察到“所有 proper subset 都行为失败而 joint 成功”的项目；这种更强条件主要由前三个补充生产接线探针展示。

“必须一起改”只针对本次真实补丁的拆分方式，不等于证明不存在另一种只改一个组件、通过兼容层解决问题的实现。

## 6. DGM 真正的自修改轨迹告诉了什么

来源：[DGM 官方仓库](https://github.com/jennyzzt/dgm)，其 README 链接的[官方实验日志](https://drive.google.com/drive/folders/1Kcu9TbIa9Z50pJ7S6hH9omzzD1pxIYZC?usp=sharing)。仓库核对版本 `a565fd2d1dca504ef5104a7cc0f3bdc4ab9b4fd2`。

日志 ZIP 约 1.01 GB；采用 HTTP Range 只取目录、40 份元数据/补丁、initial 和最早 4 条 improver 对话，没有下载整个 ZIP，也没有执行里面的生成代码。

按本实验粗粒度文件职责（loop、model I/O、tools、utils、prompts、other）分组，并排除显式 `tests/`：

- 40 个候选：37 有补丁文件，33 非空，7 缺失或为空。
- 33 个非空补丁中：22 个只改一个职责组，9 个改两个，2 个改三个。
- 20 个有整体 solver 评测分数，20 个缺失。**缺失不自动等于失败。**
- 13/20 的去重 task ID 数与报告的提交题数不一致；20 个可对照分数的父子对，其记录的 task ID 集合都不完全一致。因此无法从这些字段直接确认严格配对评测，更不能拿总分差证明组合必要性。

这里的“组件数”不是完美语义标注：一个 loop 文件可能同时包含 prompt 与控制流；同一 tools 组也可能有多项功能。它只是一致的低成本描述性统计，不是搜索空间维度估计。

实际读到的最早四条轨迹：

| 候选末尾标识 | 真实修改 | 公开整体结果 |
|---|---|---|
| `044512_397438` | loop 增加多次候选尝试、评测、选择 | 无整体分数；不能因其自述工具测试通过就称进化成功 |
| `044512_401971` | 编辑工具增加按行修改 | 15/59；不是组件消融结果 |
| `084619_287593` | 编辑工具增加行替换、插入 | 12/60 |
| `084619_293670` | loop 增加补丁有效性检查和重试反馈 | 10/59 |

此外出现过 loop + helper、model I/O + token 管理 helper 等共同修改。它们说明共同修改不是凭空设想，但**没有任何一个能仅凭公开分数证明“一起改优于所有单组件版本”**。

其他来源核查：

- [ModularRSI](https://github.com/IQuestLab/ModularRSI)：检查到发布的最终模块快照/评测轨迹，不足以还原完整逐代反事实轨迹。
- [Meta-Harness TB2 artifact](https://github.com/stanford-iris-lab/meta-harness-tbench2-artifact)：主要是最终产物，不是完整编辑历史。
- [Hyperagents](https://github.com/facebookresearch/Hyperagents)：官方日志包约 17.25 GB；本轮确认位置，未下载/执行。不把它算进已分析候选数。

## 7. 对研究方向的判断

这轮能支持的命题：

1. 禁止跨组件的单步编辑会妨碍部分真实修复。
2. prompt 模板、工具描述、解析器和运行状态应当视为有接口约束的系统，而不是互不相关的字符串。
3. 孤立单元测试可能掩盖生产接线问题，不能只看“测试全绿”来筛选进化候选。

这轮不能支持的命题：

1. 学习组织方式优于设计合理的固定模块。
2. 需要另一个高层 agent 根据进化历史拆分/合并组件。
3. 自适应分组提高 solver benchmark 成功率、跨任务泛化或单位 token 收益。

**建议止损：暂不投入大规模“学习分组”的 RSI 实验。** EgoAgent 保留模块化及跨模块事务性编辑的工程价值，先做固定边界与接口约束即可。不要因为跨组件依赖存在，就直接跳到“需要元组织学习”。

如继续科研，先换一个待证假设，而不是继续装饰本方法：例如进化评估器是否能通过生产配置回放更可靠地过滤无效候选，或者跨任务是否真需要不同 harness。它们都还需重新做文献/必要性筛查；本报告不把这些建议包装成已证实的新颖贡献。

如果以后要重启分组方向，最低证据门槛应是：多个独立真实进化谱系、相同 task/model/token 预算的父子与组件反事实、outcome-blind 的多种合理固定基线，以及组件依赖会随任务/阶段变化而固定方案持续吃亏的案例。当前没有达到。

## 9. 复现与审计

入口脚本：

- `audit_public.py`：固定样本、按范围下载公开日志、保留 SHA256。
- `analyze_dgm.py`：描述性统计；不执行 DGM 生成代码。
- `replay.py`：构造 parent / 组件子集 / full 版本，运行原样上游测试。
- `integration_probe.py`：单独记录事后生产接线探针。
- `summarize_results.py`：核对测试内容哈希、完整组合数、各方法结果；不重新选择分组。
- `test_diagnostic.py`：5 个基础设施自测，不是研究任务。

原测试使用 WSL 中的独立 venv，没有改全局 Python 依赖。具体 Python、系统与 81 个包的版本记录在本机 `results/environment.json`。`cache/`、`work/` 和 `results/` 不随 Git 发布，原始下载、源码快照与运行记录不混入产品代码。因此本文是历史诊断摘要，不是随仓库交付了全部证据的复现包；全新 clone 不能直接执行下面的汇总命令，需先按协议重新采集并运行。

已有文件下复核汇总（PowerShell，在仓库根目录）：

```powershell
python experiments/harness_edit_diagnostic_20261012/summarize_results.py
python experiments/harness_edit_diagnostic_20261012/test_diagnostic.py
```
