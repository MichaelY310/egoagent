# Chat 审批等待与工具超时修复（2026-09-15）

## 故障证据

WSL Session `code_agent_auto_20260915_141921_7bc30a99` 请求解释项目的 debug 配置。
运行记录包含 **9 次 tools 节点 NodeTimeout（300 秒）**，结束时仍保留 pending_approval。
这不是 DeepSeek 在持续思考，也不是成功回答了问题。

根因链条：

1. Workspace guard 下 shell 命令在宿主账号执行，因此被安全策略标记为高风险，要求审批。即使命令看起来只读，也不等于有 OS 级隔离。
2. 工具节点的线程超时包含了等待审批的时间。五分钟后父执行线程超时，但等待输入的线程没有停止。
3. Flow 的后续模型调用又尝试同一任务，生成新的审批；旧等待线程和新等待线程共用普通聊天输入队列。
4. 超时回滚掉该节点的记录，未完成的工具请求被历史规范化器转为 incomplete-results 提示。质量检查器没有读到文件，只能再次报告证据缺失。
5. 前端用“审批已结束”描述被新卡覆盖的旧卡；运行完成清理也遗漏了 pending_approval。

## 修复与使用

Chat 的「对话 / 改动 / 上下文」下面增加 **工具审批：手动审批** 按钮。

- 默认手动：已有低风险自动允许规则保留；需要授权的工具显示「允许一次 / 拒绝」。等待不消耗工具节点或其外层循环/子流程的执行超时。
- 点按钮并确认风险后：切成 **自动批准**。只影响当前 Session，当前已排队的工具请求也会自动批准；运行不用重启。
- 再点按钮：切回手动。已批准或开始执行的操作不会因此撤回，可以另点「停止」。
- 新 Session 默认手动，不继承另一 Session 的自动权限。当前 Session 的设置会随 Chat 配置保存，运行快照和轨迹记录实际使用的模式。

自动批准只回答权限策略的 ASK，不改变 DENY，不关闭沙箱，不解除只读模式、敏感文件或路径限制。
Flow 中显式的人工审核/输入节点不属于工具自动批准范围。
Workspace guard **不是** OS 沙箱；选择自动批准宿主命令时，命令依然具有当前账号的能力。

## 工程结构

- `runtime_waits.py`：嵌套节点共享的可暂停执行计时器；只排除人工等待，整个运行的预算/取消仍然有效。超时工作线程保留取消标记，晚到的回答不能授权已放弃的调用。
- `interactive_runs.py`：按 nonce 索引的审批请求队列和回答邮箱，与聊天输入队列彻底分离；多个子 Agent 不会互相抢审批答案。
- `interactive_execution_service.py`：单次 nonce 消费、手动/自动模式切换及停止清理；自动批准需要显式确认。
- `pipeline_engine.py`：子 Flow 的工具审批转发给根 Session；所有人工等待共用同一机制；工具执行前再次检查取消状态。
- `harness_editor/server.py`：按队列投影审批卡、记录模式变化轨迹；结束/停止后清理待审批数据。
- 原生 Chat：显示手动/自动模式和范围，区分「自动批准」「允许一次」「拒绝」「失效」；失败的设置请求不会让 UI 假装设置成功。

未放宽工作区安全策略，没有修改用户的真实项目文件，也没有重写历史失败记录。
